# AGENTS.md

Инструкции в этом файле действуют для всего репозитория.

## Контекст проекта

`cringe-pics-telebot` — асинхронный Telegram-бот на Python 3.14 и aiogram 3. Основные внешние зависимости: PostgreSQL через SQLAlchemy/asyncpg, Redis и API Яндекс Диска. Зависимостями и командами проекта управляет `uv`.

Основные каталоги:

- `src/cringe_pics_telebot/bot/` — Telegram handlers, middleware, callback data и клавиатуры;
- `src/cringe_pics_telebot/services/` — бизнес-логика и оркестрация сценариев;
- `src/cringe_pics_telebot/repositories/` — доступ к PostgreSQL, Redis и Яндекс Диску;
- `src/cringe_pics_telebot/entities/` и `repositories/**/entities/` — модели данных;
- `alembic/` — миграции PostgreSQL;
- `tests/functional/` — функциональные тесты с реальными PostgreSQL/Redis и fake HTTP API;
- `tests/units/` — изолированные тесты простой детерминированной логики.

## Общие правила изменений

- Делай минимальные изменения, решающие задачу в корне, и сохраняй существующую архитектуру.
- Не смешивай рефакторинг, не относящийся к задаче, с фичей или фиксом.
- Поддерживай Python 3.14 и асинхронный стиль проекта. Не добавляй синхронный I/O в async-пути.
- Добавляй точные аннотации типов. Для абстракций коллекций и callable предпочитай `collections.abc`; используй современные типы и синтаксис Python.
- Для структур данных предпочитай `dataclass`; используй `slots=True`, а для неизменяемых value objects — также `frozen=True`, если это соответствует модели.
- Пользовательские тексты бота и `README.md` ведутся на русском языке.
- Не добавляй секреты и реальные токены. Локальные `.env` должны оставаться вне Git.
- Для ожидаемых сбоев делай ошибки и логи диагностичными. Не подавляй `asyncio.CancelledError`: освободи ресурс при необходимости и пробрось отмену дальше.

## Архитектура и работа с данными

- Telegram-слой должен оставаться тонким: разобрать update, проверить доступ, вызвать сервис и сформировать ответ.
- Бизнес-правила и orchestration размещай в `services/`, а не в handlers или репозиториях.
- Репозитории отвечают за операции с конкретным хранилищем и преобразование строк/ответов во внутренние модели. Не переноси в них бизнес-сценарии только ради сокращения service-функции.
- Предпочитай небольшие атомарные репозиторные функции. Объединяй сложную логику в один SQL-запрос только когда это необходимо для атомарности, конкурентной корректности, блокировки или заметной эффективности.
- Границы транзакций задавай в слое бизнес-логики (`services/`) вокруг полного изменения бизнес-состояния через `async with transaction():`.
- Репозиторные функции не должны самостоятельно делать `commit`/`rollback` или скрыто определять границы составного бизнес-сценария.
- Не удерживай транзакцию PostgreSQL во время запросов к Telegram, Яндекс Диску, Redis или другого медленного сетевого I/O. Сетевой вызов и короткие транзакционные изменения состояния разделяй.
- Для конкурентных сценариев сохраняй существующие подходы: транзакции и row locks в PostgreSQL, атомарные reserve/update-запросы, Redis lease/dedupe с проверкой token/value.
- При изменении схемы добавляй новую Alembic-миграцию. Не переписывай уже применявшиеся миграции без явной необходимости и обязательно проверяй upgrade на реальной PostgreSQL.

## Тестирование

### Выбор уровня теста

- По умолчанию предпочитай функциональный тест, проверяющий пользовательский или бизнес-сценарий через реальные границы приложения.
- Пиши unit-тесты только для относительно простой и детерминированной логики: parsing, formatting, validation, pure policy/selection functions и небольшие преобразования данных.
- Если unit-тест требует большого количества моков или повторяет внутреннюю реализацию, подними его на функциональный уровень.
- В функциональных тестах используй существующие fixtures и fake-сервисы из `tests/functional/conftest.py`, `fake_telegram.py`, `fake_yandex.py` и `fake_statsd.py`. Предпочитай fake внешнего протокола мокам внутренних функций.
- Проверяй наблюдаемое поведение и сохранённое состояние, а не последовательность внутренних вызовов, если она не является частью контракта.

### Assertions и организация cases

- Для содержательных проверок используй `pyhamcrest`: `assert_that` и подходящие matchers (`equal_to`, `contains_string`, `has_entries`, `empty`, `none`, `same_instance` и т. п.).
- Не используй Hamcrest механически. Для одной очевидной проверки примитивного `int`, `str`, `bool` или другого простого значения лаконичный `assert actual == expected` предпочтительнее громоздкого matcher-выражения.
- Если несколько тестов выражают одно правило и отличаются только входными данными/ожидаемым результатом, объединяй их через `pytest.mark.parametrize`.
- Не объединяй параметризацией сценарии с принципиально разным setup, потоком действий или смыслом ошибки.
- Имена тестов должны описывать поведение и ожидаемый результат. Для async-тестов полагайся на настроенный `asyncio_mode = auto`.
- Для исправления бага добавляй регрессионный тест, который падает без фикса.

## README и коммиты

- После каждой фичи или фикса проверь, изменился ли любой аспект, описанный в `README.md`: поведение бота, команды, конфигурация, переменные окружения, схема данных, запуск, миграции, эксплуатация или деплой.
- Если описанный аспект изменился, обновление `README.md` обязательно.
- Изменение `README.md` оформляй отдельным документационным коммитом после коммита с фичей/фиксом. Не включай README в функциональный коммит.
- Если задача не предполагает создание коммитов, всё равно обнови `README.md`, но явно сообщи, что его diff должен быть закоммичен отдельно.
- Коммиты делай атомарными и не включай в них посторонние локальные изменения. Не создавай коммиты без явного запроса пользователя или workflow, который прямо требует коммиты.

## Стиль и инструменты

Ruff настроен на длину строки 120 и правила `E`, `F`, `B`, `I`, `UP`, `SIM`. Pre-commit также запускает Ruff formatter и базовые проверки файлов.

Установка окружения, эквивалентная CI:

```bash
uv sync --locked --all-extras --dev
```

Начинай проверку с самого узкого затронутого теста, затем запускай соответствующий набор. Перед завершением изменения по возможности выполни:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest tests/units -q
uv run pytest tests/functional -q
```

Функциональные тесты требуют работающий Docker: fixtures сами поднимают PostgreSQL 18 и Redis через `tests/functional/compose.functional-tests.yml` на свободных локальных портах.

Если полный набор запустить нельзя, выполни максимально близкую доступную проверку и явно укажи, что именно не запускалось и почему. Не утверждай, что проверка прошла, если команда не выполнялась успешно.
