# cringe-pics-telebot

Telegram-бот, который присылает кринжовые картинки и GIF из коллекции на Яндекс Диске. Медиа можно запросить вручную, получать по расписанию или отправлять в любой чат через inline-режим.

## Возможности

- `/start` и `/help` показывают актуальные категории, команды и клавиатуру быстрого доступа;
- кнопка активной категории отправляет случайное медиа из соответствующей папки независимо от наличия расписания. Для каждого пользователя изображения не повторяются до полного прохода актуального состава категории;
- `/list` и `/subscriptions` позволяют подписаться на плановые категории и отписаться от них. Рядом со временем показываются дни отправки: `ежедневно` либо, например, `Пн, Ср, Пт`. Бот продолжает тот же пользовательский цикл, что и ручные запросы; категории без расписания в списке отсутствуют;
- `/timezone [+HH:MM]` показывает или меняет фиксированное UTC-смещение пользователя. Время и день недели каждой категории применяются к локальной дате пользователя в выбранном часовом поясе; значение по умолчанию — `+07:00`;
- администраторы открывают закрытую панель командой `/admin` или отдельной reply-кнопкой, управляют категориями, вручную синхронизируют медиа-каталог и создают, редактируют и удаляют разовые уведомления;
- разовое уведомление без явно указанного UTC-смещения приходит в заданные дату и время отдельно по локальному часовому поясу каждого пользователя. Явное смещение, например `+07:00`, назначает единый момент отправки для всех;
- inline-запрос вида `@имя_бота day` ищет все активные категории по части названия независимо от наличия расписания и постранично показывает картинки и GIF. Первая страница содержит до 50 результатов вместе с `🎲 Выбрать случайную картинку`, следующие — до 50 обычных результатов;
- метаданные коллекции периодически синхронизируются с Яндекс Диска в PostgreSQL. При первой реальной отправке нового медиа Telegram получает временный URL, а возвращённые `file_id` и `file_unique_id` сохраняются в каталоге; следующие отправки используют только `file_id`;
- Redis защищает рассылки от дублей и координирует короткие распределённые lease синхронизации и первой отправки, но не является хранилищем `file_id`.

Категории не зашиты в коде: их названия, nullable-локальное время рассылки, дни недели, папки с медиа и признак активности хранятся в PostgreSQL. Непустое `subscription_types.time` задаёт плановую категорию, доступную для ordinary-выдачи, подписок и inline-режима; scheduler отправляет её только при одновременном совпадении локальных времени и дня недели пользователя. `NULL` отключает подписки и плановые отправки, но сохраняет выбранные дни и ordinary-выдачу через reply-кнопку или сообщение с именем категории, а также поиск по имени/алиасам в inline-режиме. Неактивные категории недоступны пользователям, не участвуют в inline-поиске и плановых отправках, но продолжают синхронизировать медиа-каталог. Там же находится синхронизированный каталог медиа и Telegram `file_id`, поэтому прогретая ручная, автоматическая и inline-отправка не обращается к Яндекс Диску. Новые и изменённые файлы остаются `pending` до первой успешной отправки реальному получателю; отдельный служебный Telegram-чат для загрузки не нужен. Выбранное UTC-смещение также хранится в PostgreSQL отдельно для каждого пользователя. В базе находятся и список администраторов, и разовые уведомления с историей попыток доставки. Поэтому настройки, каталог и запланированные сообщения сохраняются после перезапуска приложения.

PostgreSQL также хранит независимый случайный цикл для каждой пары «пользователь — категория». Ручные и плановые отправки используют одну историю: пока состав категории не меняется, каждое медиа успешно отправляется один раз до начала следующего цикла, а при размере категории больше одного первая картинка нового цикла не совпадает с последней картинкой предыдущего. Добавленный файл сразу входит в незавершённый цикл, удалённый перестаёт участвовать и не блокирует его завершение; возвращённый по тому же пути файл считается тем же медиа. Inline-выдача эту историю не читает и не изменяет, поскольку бот не знает, какой inline-result пользователь фактически отправил.

Перед ordinary- или плановой отправкой бот короткой транзакцией резервирует медиа для конкретной пары, завершает транзакцию и только затем обращается к Telegram. Успешная отправка подтверждается отдельной короткой транзакцией; обработанная ошибка или отмена освобождает резерв, а оставшийся после аварийного завершения процесса резерв становится доступен через пять минут. Между успешным ответом Telegram и подтверждением PostgreSQL остаётся небольшое неизбежное окно: если процесс завершится именно в этот момент, после истечения резерва медиа может быть показано повторно, поскольку Telegram и PostgreSQL не поддерживают общую exactly-once транзакцию.

Получатели разового административного уведомления — все активные пользователи, которые взаимодействовали с ботом в private-чате, даже если они не подписаны ни на одну категорию. Если Telegram сообщает, что пользователь заблокировал бота или деактивировал аккаунт, пользователь исключается из следующих административных уведомлений, но его часовой пояс и подписки сохраняются. Новое private-сообщение автоматически возвращает пользователя в активную аудиторию.

Для inline-режима владелец бота должен один раз включить его через [@BotFather](https://t.me/BotFather): выполнить `/setinline`, выбрать бота и задать текст-подсказку для поля ввода.

Продолжение inline-выдачи загружается штатной пагинацией Telegram. Первая страница содержит специальный случайный результат и до 49 обычных, а следующие страницы — до 50 обычных результатов. Бот передаёт между страницами самодостаточный версионированный cursor с seed последовательности и числовой позицией; cursor привязан к нормализованному тексту запроса, укладывается в ограничение Telegram 64 байта и не хранится в Redis. Отдельного TTL у cursor нет: он остаётся формально действительным для того же запроса, пока бот поддерживает его версию.

Отсутствие повторов и пропусков гарантируется, пока между страницами не меняются дедуплицированный каталог подходящих медиа и состояние их готовности в Telegram. Изменения каталога обрабатываются best effort без серверного snapshot. Невалидный, слишком длинный, неизвестной версии или относящийся к другому запросу cursor не перезапускает последовательность с произвольной позиции: бот возвращает пустую последнюю страницу. Временные URL запрашиваются только для медиа текущей страницы, а не для уже пройденных или ещё не показанных результатов.

## Технологии

- **Python 3.14** и [aiogram 3](https://docs.aiogram.dev/) — асинхронный Telegram-бот в режиме long polling;
- **aiohttp** — работа с REST API Яндекс Диска;
- **PostgreSQL 18**, **SQLAlchemy 2.1** и **asyncpg** — категории, медиа-каталог, Telegram `file_id`, пользовательские циклы и подписки;
- **Redis** с **hiredis** — защита рассылок от дублирования и распределённые lease;
- **uv** — управление зависимостями и запуск приложения;
- **Docker Compose** — запуск бота, PostgreSQL и Redis;
- **pytest**, **Ruff** и **mypy** — функциональные тесты, линтинг и проверка типов в CI.

## Развёртывание на своём сервере

### Что понадобится

- Linux-сервер с Git, Docker Engine и Docker Compose v2;
- PostgreSQL 18: миграция медиа-каталога использует виртуальную generated-колонку, которой нет в более старых версиях;
- Telegram-бот и его токен от [@BotFather](https://t.me/BotFather);
- OAuth-токен Яндекс Диска с доступом к папке приложения;
- исходящие HTTPS-подключения к Telegram Bot API и API Яндекс Диска.

Входящий HTTP-порт для бота открывать не нужно: обновления Telegram он получает через long polling. Файл `compose.yml` публикует PostgreSQL на порту `4243`, а Redis — на `12312`; ограничьте доступ к ним сетевым экраном сервера, если эти порты не нужны извне.

### 1. Получить проект

```bash
git clone https://github.com/progbagger/cringe-pics-telebot.git
cd cringe-pics-telebot
```

### 2. Настроить переменные окружения

Создайте четыре обязательных файла. Они игнорируются Git и не должны попадать в репозиторий.

`docker/bot/.env`:

```dotenv
TELEGRAM_BOT_TOKEN=<токен Telegram-бота>
```

`docker/postgres/.env`:

```dotenv
POSTGRES_USER=cringe_bot
POSTGRES_PASSWORD=<надёжный пароль PostgreSQL>
POSTGRES_DB=cringe_bot
POSTGRES_HOST=postgres
```

`docker/redis/.env`:

```dotenv
REDIS_USERNAME=cringe_bot
REDIS_PASSWORD=<надёжный пароль Redis>
REDIS_HOST=redis
```

`docker/yandex/.env`:

```dotenv
YANDEX_DISK_TOKEN=<OAuth-токен Яндекс Диска>
```

Чтобы отправлять метрики на существующий внешний Graphite/StatsD, скопируйте пример и укажите доступный из bot container адрес StatsD:

```bash
cp docker/statsd/.env.example docker/statsd/.env
```

```dotenv
STATSD_HOST=statsd.example.com
STATSD_PORT=8125
STATSD_PREFIX=cringe_pics_telebot
```

StatsD использует UDP. Проект не запускает Graphite и не управляет его хранилищем или dashboard; на внешнем сервере и в firewall должен быть разрешён UDP-трафик от bot host к указанному порту. Если `docker/statsd/.env` отсутствует, метрики отключены. Если endpoint настроен, но port некорректен или адрес не разрешается, бот завершает startup с явной ошибкой конфигурации. Ошибка UDP-отправки после успешного запуска не останавливает polling.

Дополнительно в `docker/bot/.env` можно задать:

- `LOG_LEVEL_NAME`;
- `SUBSCRIPTION_BROADCAST_INTERVAL_SECONDS` и `ADMIN_BROADCAST_INTERVAL_SECONDS` — интервалы проверки периодических рассылок и административных уведомлений соответственно, по умолчанию 30 секунд; допустимы значения больше нуля и не более 60 секунд;
- `MEDIA_SYNC_INTERVAL_SECONDS` — интервал синхронизации метаданных с Яндекс Диском, по умолчанию `43200` секунд (12 часов). Первый проход выполняется сразу после запуска; значение должно быть больше нуля.

### 3. Подготовить медиа на Яндекс Диске

Создайте в папке приложения на Яндекс Диске каталоги категорий и загрузите туда изображения или GIF. Для стандартного набора это:

```text
morning/
day/
evening/
night/
random/
```

Имена каталогов должны совпадать со значениями `s3_directory_path` в таблице `subscription_types` из шага добавления категорий.

### 4. Запустить сервисы

Production Compose закреплён на PostgreSQL 18. Если существующий volume создан PostgreSQL 17 или более ранней версией, сначала сделайте резервную копию и перенесите кластер в PostgreSQL 18 через `pg_upgrade` или dump/restore. Нельзя подключать `postgres:18` непосредственно к data directory старой major-версии. На чистой установке дополнительных действий не требуется.

```bash
docker compose run --rm bot uv run --isolated --no-dev --group migration alembic upgrade head
docker compose up -d --build
docker compose ps
docker compose logs -f bot
```

Миграции Alembic запускаются отдельной одноразовой командой и не входят в production-зависимости процесса бота. После запуска polling можно остановить просмотр логов сочетанием `Ctrl+C` — контейнеры продолжат работать.

### 5. Добавить администраторов

Список администраторов хранится в таблице `administrators`. Получите Telegram user ID нужного пользователя и добавьте его следующей командой, заменив `123456789` реальным значением:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
INSERT INTO administrators (user_id)
VALUES (123456789)
ON CONFLICT (user_id) DO NOTHING;
SQL
```

Права применяются без перезапуска бота. Чтобы отозвать их, удалите только запись из `administrators`:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
DELETE FROM administrators WHERE user_id = 123456789;
SQL
```

После добавления ID пользователь увидит кнопку **Админ-панель** при следующем `/start` или другом сообщении, которое показывает основную клавиатуру. Команда `/admin` доступна сразу. Для остальных пользователей команда и текст кнопки обрабатываются как неизвестное сообщение.

### 6. Добавить категории

Пример ниже создаёт стандартные категории и задаёт локальное время рассылок. Повторный запуск команды обновит существующие записи.

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
INSERT INTO subscription_types (
    name,
    time,
    weekdays,
    s3_directory_path,
    search_aliases,
    is_active,
    created_at,
    updated_at
)
VALUES
    ('random',  '00:00:00', 127, 'random',  ARRAY['рандом', 'случайная'],        true, now(), now()),
    ('morning', '08:00:00', 127, 'morning', ARRAY['утро', 'утренняя', 'с утра'], true, now(), now()),
    ('day',     '13:00:00', 127, 'day',     ARRAY['день', 'дневная'],            true, now(), now()),
    ('evening', '19:00:00', 127, 'evening', ARRAY['вечер', 'вечерняя'],          true, now(), now()),
    ('night',   '23:00:00', 127, 'night',   ARRAY['ночь', 'ночная'],             true, now(), now())
ON CONFLICT (name) DO UPDATE
SET time = EXCLUDED.time,
    weekdays = EXCLUDED.weekdays,
    s3_directory_path = EXCLUDED.s3_directory_path,
    search_aliases = EXCLUDED.search_aliases,
    updated_at = now();
SQL
```

Название активной категории используется в подписи кнопки и в inline-поиске независимо от наличия расписания; добавлять к нему `/` не нужно. `search_aliases` задаёт дополнительные термины только для inline-поиска: запрос сопоставляется с именем и каждым алиасом без учёта регистра, по частичному совпадению. Алиасы не создают отдельные кнопки или подписки и не влияют на обычные сообщения.

Время указывается без UTC-смещения. `weekdays` — битовая маска ISO-дней: младший бит означает понедельник, следующий — вторник, …, седьмой — воскресенье. Значение `127` включает все семь дней, а `21` соответствует `Пн, Ср, Пт`. Допустимы только значения `1..127`; пустое расписание PostgreSQL отклоняет. Постоянный server default равен `127`, поэтому прямой `INSERT` без `weekdays` создаёт ежедневную категорию. Scheduler вычисляет локальные дату и время отдельно для каждого подписчика, поэтому в один UTC-момент решение может различаться по обе стороны полуночи.

Значение `NULL` вместо времени создаёт категорию без расписания: после активации она появится в reply-клавиатуре и inline-режиме, но не в подписках или scheduler. Сохранённая маска дней при этом не очищается и снова применяется после задания времени. Путь задаётся относительно папки приложения на Яндекс Диске. Категория `random` в этом примере является отдельной коллекцией и отдельной рассылкой; при необходимости её можно удалить или настроить как любую другую категорию.

На уровне PostgreSQL новые категории имеют `is_active = false` по умолчанию. Пример выше явно активирует первоначальный стандартный набор. Повторный запуск команды обновляет поля категории, но намеренно не меняет `is_active`, поэтому не включит категорию, которую администратор ранее деактивировал.

После первоначального добавления категорий откройте `/admin` и нажмите **Синхронизировать медиа**, чтобы немедленно выполнить первый metadata-sync без перезапуска бота. После завершения отправьте боту `/start`.

При необходимости смените часовой пояс командой, например `/timezone +04:00`. Последующие добавления, изменения и удаления файлов попадут в каталог при очередном автоматическом sync или после ручного запуска из админ-панели; период фоновой синхронизации задаётся `MEDIA_SYNC_INTERVAL_SECONDS`. Ошибка чтения одной папки не деактивирует её предыдущий успешный snapshot. Для проверки состояния и логов используйте:

```bash
docker compose ps
docker compose logs --tail=100 bot
```

Обновление установленной версии выполняется так:

```bash
git pull --ff-only
docker compose run --rm bot uv run --isolated --no-dev --group migration alembic upgrade head
docker compose up -d --build --remove-orphans
```

При запуске без Docker Compose сначала примените миграции командой `uv run --isolated --no-dev --group migration alembic upgrade head`, а затем запустите бота командой `uv run --no-dev bot`.

Данные PostgreSQL, включая медиа-каталог, Telegram `file_id` и пользовательские циклы отправки, а также виртуальное окружение бота сохраняются в Docker volumes `pg-data` и `bot-env`. Redis содержит только восстанавливаемые dedupe/lease-ключи и отдельного volume не имеет.

## Управление категориями через админ-панель

Администратор может открыть **Админ-панель → Управление категориями**, увидеть статусы всех категорий и создать новую. Для режима **По расписанию** бот последовательно запрашивает название, путь к каталогу на Яндекс Диске, режим отправки, локальное время в формате `ЧЧ:ММ`, дни недели и поисковые алиасы. Дни переключаются кнопками `Пн`…`Вс`; **Готово** принимает непустой выбор, а **Каждый день** выбирает все семь дней и сразу продолжает форму. Для режима **Без расписания** шаги времени и дней пропускаются, а сохранённое расписание дней по умолчанию остаётся ежедневным. До заполнения последнего шага данные находятся только в черновике FSM; отмена не создаёт частичную запись. Новая категория всегда создаётся неактивной.

Карточка категории показывает её статус, путь, время либо пометку «без расписания», дни (`каждый день` или список вроде `Пн, Ср, Пт`) и алиасы. Для плановой категории кнопка **Изменить дни отправки** открывает ту же клавиатуру с текущим выбором; PostgreSQL обновляется только после **Готово** или **Каждый день**, а отмена оставляет прежние дни. **Изменить время отправки** задаёт новое `ЧЧ:ММ` или повторно включает расписание, а отдельная кнопка **Отключить расписание** отключает подписки и плановые отправки категории, сохраняя выбранные дни, ordinary- и inline-выдачу. Существующие подписки при отключении не удаляются: они скрываются и не исполняются, а после повторного задания времени снова становятся видимыми и действующими с прежними днями.

Кнопки **Активировать** и **Деактивировать** управляют доступностью категории без перезапуска бота. Неактивная категория исчезает из пользовательских кнопок, списка подписок и inline-поиска, а плановые отправки для неё приостанавливаются. Медиа-каталог и существующие подписки при этом не удаляются: каталог продолжает синхронизироваться, а после повторной активации сохранённые подписки снова действуют.

Алиасы вводятся по одному на строку; пробелы внутри строки сохраняются, а пустые строки и повторы без учёта регистра игнорируются. Кнопка **Очистить алиасы** удаляет весь дополнительный словарь, не меняя основное имя, статус, подписки, расписание или путь к медиа. Первичную инициализацию и идемпотентное массовое обновление категорий по-прежнему удобнее выполнять SQL-командой из раздела выше.

### Ручная синхронизация медиа

Кнопка **Синхронизировать медиа** находится на верхнем уровне админ-панели. Бот сразу подтверждает запуск, а затем обходит все категории, включая неактивные, и показывает сводку: количество обработанных категорий и ошибок, найденных медиа, созданных и изменённых записей, повторно активированных медиа и деактивированных отсутствующих файлов. Ошибка отдельной категории отображается как частично успешный результат и не скрывает счётчики успешно обработанных категорий.

Ручной и фоновый запуски используют один Redis lease и не выполняются параллельно. Если синхронизация уже идёт, новый обход не начинается, а администратор получает понятное уведомление. После любого результата можно запустить синхронизацию повторно или вернуться в админ-панель.

## Разовые административные уведомления

Откройте `/admin`, выберите **Уведомления** и отправьте боту сообщение, которое нужно скопировать получателям. Поддерживаются типы сообщений, доступные методу Telegram `copyMessage`; исходное сообщение нельзя удалять до завершения отправки уведомления.

Дата вводится одним из двух способов:

```text
20.08.2099 10:00
20.08.2099 10:00 +07:00
```

В первом варианте каждый получатель получает сообщение, когда `10:00` наступает в его сохранённом часовом поясе. Во втором все получают сообщение одновременно — в момент, соответствующий `10:00 UTC+07:00`. Допустимые фиксированные смещения: от `-12:00` до `+14:00`.

После даты бот предлагает указать до 1000 дополнительных Telegram user ID через пробелы, запятые или переносы строк. Этот список нужен, например, для разовой отправки пользователям, которых старая версия бота ещё не сохраняла. Дополнительные ID относятся только к выбранному уведомлению и не делают пользователя постоянным получателем следующих. Если для ID ещё нет сохранённого часового пояса, используется значение по умолчанию `UTC+07:00`; явное смещение в дате по-прежнему задаёт один момент для всех. Шаг можно пропустить inline-кнопкой, а список — позднее изменить до начала отправки.

До начала первой доставки уведомление можно редактировать или удалить inline-кнопками. После начала отправки редактирование блокируется, чтобы пользователи разных часовых поясов не получили разные версии. Удаление является мягким: запись получает статус `deleted`, а завершённое уведомление — `completed`. Сами уведомления и результаты попыток остаются в PostgreSQL, хотя экран истории в текущей версии отсутствует.

Перед каждым сетевым запросом бот атомарно резервирует одну попытку для пары «уведомление — пользователь», поэтому повторная проверка scheduler-а не создаёт дубль. Автоматических повторов после ошибки нет; сбой одному получателю сохраняется в истории и не останавливает отправку остальным.

## Автоматический деплой через GitHub Actions

Workflow **Deploy over SSH** автоматически обновляет сервер после merge pull request в `main`, если workflow **CI** успешно проверил итоговый commit и были изменены файлы приложения или production-сборки:

- `src/**`;
- `docker/**`;
- `pyproject.toml` или `uv.lock`;
- `compose.yml`.

Изменения только в документации, тестах и служебных файлах деплой не запускают. Workflow также можно запустить вручную через `workflow_dispatch`; ручной запуск не зависит от списка изменённых файлов.

В GitHub environment с именем **Deploy** нужно создать secrets:

- `DEPLOY_HOST` — адрес сервера;
- `DEPLOY_USER` — SSH-пользователь;
- `DEPLOY_SSH_KEY` — приватный SSH-ключ;
- `DEPLOY_PORT` — SSH-порт, если используется не `22`;
- `DEPLOY_PATH` — путь к checkout репозитория на сервере, если он отличается от `cringe-pics-telebot`.

Перед первым автоматическим деплоем репозиторий, `.env`-файлы, категории PostgreSQL и папки Яндекс Диска нужно подготовить вручную по инструкции выше. Workflow разворачивает конкретный commit, применяет миграции отдельным one-shot контейнером и перезапускает сервисы через Docker Compose.
