# cringe-pics-telebot

Telegram-бот, который присылает кринжовые картинки, GIF и MP4-видео из коллекции на Яндекс Диске. Медиа можно запросить вручную, получать по расписанию или отправлять в любой чат через inline-режим.

## Возможности

- `/start` и `/help` показывают категории, команды и клавиатуру быстрого доступа;
- кнопка активной категории отправляет случайное медиа из соответствующей папки независимо от наличия расписания. Бот сразу показывает «Выбираю картинку», а после выбора заменяет это же сообщение фотографией, GIF или MP4. Для каждого пользователя изображения не повторяются до полного прохода актуального состава категории;
- `/list` и `/subscriptions` позволяют подписаться на плановые категории и отписаться от них. Администратор может объединить категории в одноуровневые папки: внутри доступны отдельные переключатели, **Подписаться на все**, **Отписаться от всех** и **Назад**. Корневой список и содержимое папки разбиваются на страницы по восемь элементов и сохраняют открытую страницу после изменения подписки. Рядом со временем показывается периодичность: `ежедневно`, список дней вроде `Пн, Ср, Пт`, `ежегодно 01.01` или `ежегодно в твой день рождения`. Пользователь без сохранённой даты видит подсказку о `/birthday`, но может заранее подписаться на birthday-категорию. Бот продолжает тот же пользовательский цикл, что и ручные запросы; категории без времени в списке отсутствуют;
- `/timezone [+HH:MM]` показывает или меняет фиксированное UTC-смещение пользователя. Время, день недели и ежегодная календарная дата категории применяются к локальной дате пользователя в выбранном часовом поясе; значение по умолчанию — `+07:00`;
- `/birthday [DD.MM|clear]` показывает, вручную задаёт или удаляет день и месяц рождения. Ручное значение имеет приоритет над датой из профиля Telegram;
- администраторы открывают закрытую панель командой `/admin` или отдельной reply-кнопкой, управляют категориями и папками подписок, вручную синхронизируют медиа-каталог и дни рождения из профилей Telegram, а также создают, редактируют и удаляют разовые уведомления;
- разовое уведомление без явно указанного UTC-смещения приходит в заданные дату и время отдельно по локальному часовому поясу каждого пользователя. Явное смещение, например `+07:00`, назначает единый момент отправки для всех;
- inline-режим сохраняет поиск категорий по части имени и добавляет поиск конкретных медиа по контекстным алиасам: глобально либо внутри категории, указанной первым словом. Выдача содержит фото, GIF и уже прогретые MP4 и продолжается штатной пагинацией Telegram;
- опциональный фоновый worker автоматически добавляет алиасы медиа через удалённую vision-модель Ollama. Задания сохраняются в PostgreSQL, а ручные алиасы имеют приоритет; отправки и inline-поиск не ждут модель;
- единый фоновый цикл последовательно синхронизирует метаданные коллекции с Яндекс Диска и дни рождения из профилей Telegram. При первой реальной отправке нового медиа, включая MP4, Telegram получает временный URL. Совместимые с ожидаемым типом `file_id` и `file_unique_id` сохраняются в каталоге; после этого следующие отправки используют только `file_id`;
- Redis защищает рассылки от дублей и координирует независимые короткие распределённые lease синхронизации медиа, профилей и первой отправки, но не является хранилищем `file_id`.

Основная reply-клавиатура обновляется с новым поддерживаемым сообщением в private-чате: ответом на команду, плановой отправкой медиа, разовым административным уведомлением. Версия с кнопкой **Админ-панель** выбирается по роли получателя, в том числе при копировании уведомления из другого чата. Явно заданная inline-клавиатура, специальная reply-клавиатура, `ForceReply` или `ReplyKeyboardRemove` имеют приоритет. Служебное сообщение «Выбираю картинку» при ручном запросе отправляется без reply-клавиатуры, чтобы Telegram разрешил заменить его выбранным медиа; уже показанная пользователю клавиатура при этом не удаляется. Редактирование сообщений, альбомы и callback-only операции не отправляют дополнительное сообщение ради обновления кнопок; в группах, каналах и сообщениях от имени business account основная клавиатура не добавляется. Плановая отправка обновляет клавиатуру без reply или упоминания пользователя (`selective=False`); режим постоянного отображения клавиатуры не включается.

Каждый процесс бота кеширует общий состав активных категорий и роли для интерфейса на **60 секунд** и переиспользует обычную и административную версии клавиатуры. Использование снимка не продлевает TTL: следующая подходящая отправка после истечения срока перечитывает данные, включая изменения через SQL или другой процесс. Поэтому кнопки могут отставать от изменений до следующей отправки после TTL. Проверки доступа к `/admin` и административным callback выполняются независимо от кеша интерфейса и сразу учитывают отзыв роли.

Категории не зашиты в коде: их названия, nullable-локальное время рассылки, вид расписания, дни недели или фиксированная ежегодная дата, папки с медиа и признак активности хранятся в PostgreSQL. Поддерживаются `weekly`, `annual_date` и `annual_birthday`. Непустое `subscription_types.time` включает плановую отправку: scheduler всегда проверяет локальные часы и минуты пользователя, а затем — дни недели, фиксированные month/day категории либо month/day рождения подписчика. `NULL` временно скрывает категорию из списка подписок и отключает scheduler, но сохраняет вид расписания, его параметры, существующие подписки и ordinary-выдачу через reply-кнопку или сообщение с именем категории, а также поиск по имени/алиасам в inline-режиме. Неактивные категории недоступны пользователям, не участвуют в inline-поиске и плановых отправках, но продолжают синхронизировать медиа-каталог. Там же находится синхронизированный каталог медиа, Telegram `file_id` и контекстные алиасы каждого медиа, поэтому прогретая ручная, автоматическая и inline-отправка не обращается к Яндекс Диску. Контекстные алиасы хранятся в отдельной таблице `media_search_aliases` и не теряются при обновлении, временном исчезновении или повторном появлении файла. Новые и изменённые файлы остаются `pending` до успешного сохранения совместимых Telegram IDs после реальной отправки получателю; отдельный служебный Telegram-чат для загрузки не нужен. Фото и GIF в этом состоянии доступны inline по временному URL, а MP4 появляется в inline-выдаче только после такой ordinary- или плановой materialization: Telegram требует для URL-based video отдельный JPEG-thumbnail, который бот не генерирует. Выбранное UTC-смещение и nullable-дата рождения также хранятся в PostgreSQL отдельно для каждого пользователя. В базе находятся и список администраторов, и разовые уведомления с историей попыток доставки. Поэтому настройки, каталог и запланированные сообщения сохраняются после перезапуска приложения.

Папки подписок хранятся отдельно в `subscription_category_folders` и связываются с низкоуровневыми категориями через `subscription_category_folder_members`. Они организуют только `/list` и `/subscriptions`: папка не имеет пути на Яндекс Диске, расписания, алиасов или медиа и не появляется в reply-клавиатуре, `/start` и inline-поиске. В этих интерфейсах входящие в неё категории продолжают работать самостоятельно.

PostgreSQL также хранит независимый случайный цикл для каждой пары «пользователь — категория». Ручные и плановые отправки используют одну историю: пока состав категории не меняется, каждое медиа успешно отправляется один раз до начала следующего цикла, а при размере категории больше одного первое медиа нового цикла не совпадает с последним медиа предыдущего. Добавленный файл сразу входит в незавершённый цикл, удалённый перестаёт участвовать и не блокирует его завершение; возвращённый по тому же пути файл считается тем же медиа. Inline-выдача эту историю не читает и не изменяет, поскольку бот не знает, какой inline-result пользователь фактически отправил.

Перед ordinary- или плановой отправкой бот короткой транзакцией резервирует медиа для конкретной пары, завершает транзакцию и только затем обращается к Telegram. Полученный `Message` фиксирует успешную доставку и позволяет подтвердить резерв отдельной короткой транзакцией. Извлечение и сохранение reusable Telegram IDs выполняются после доставки как best effort: если в ответе нет ожидаемого `photo`/`animation`/`video` либо запись IDs не удалась, каталог остаётся `pending`, несовместимый ID не сохраняется и повторный Telegram request в рамках этой попытки не выполняется. Сбой materialization записывается без временного URL, Telegram IDs, токена и полного ответа. Ошибка до получения `Message` или отмена освобождает резерв, а оставшийся после аварийного завершения процесса резерв становится доступен через пять минут. Между успешным ответом Telegram и подтверждением PostgreSQL остаётся небольшое неизбежное окно: если процесс завершится именно в этот момент, после истечения резерва медиа может быть показано повторно, поскольку Telegram и PostgreSQL не поддерживают общую exactly-once транзакцию.

Получатели разового административного уведомления — все активные пользователи, которые взаимодействовали с ботом в private-чате, даже если они не подписаны ни на одну категорию. Если Telegram сообщает, что пользователь заблокировал бота или деактивировал аккаунт, пользователь исключается из следующих административных уведомлений, но его часовой пояс и подписки сохраняются. Новое private-сообщение автоматически возвращает пользователя в активную аудиторию.

Для inline-режима владелец бота должен один раз включить его через [@BotFather](https://t.me/BotFather): выполнить `/setinline`, выбрать бота и задать текст-подсказку для поля ввода.

### День рождения пользователя

Команда `/birthday` показывает сохранённые день и месяц вместе с источником: значение указано вручную или получено из Telegram. `/birthday DD.MM` принимает строгий формат из двух цифр для дня и месяца, например `/birthday 31.12`; внешние пробелы игнорируются, год не принимается, а `29.02` считается допустимой датой. `/birthday clear` удаляет дату независимо от источника, после чего следующий проход синхронизации снова сможет получить её из профиля Telegram.

Бот хранит только `users.birth_month`, `users.birth_day` и `users.birthdate_source`, добавленные миграцией `0015`: год рождения, имя и другие данные профиля не сохраняются. Ручной ввод добровольный и имеет безусловный приоритет — фоновая синхронизация не запрашивает профиль пользователя с ручным значением и повторно проверяет источник перед записью. Бот не пишет пользователю отдельные запросы или напоминания: доступная Telegram birthdate читается в фоне через `getChat` и используется ежегодными birthday-категориями.

### Inline-поиск

В inline-режиме алиасы категорий и алиасы медиа имеют разное назначение. Алиас категории, например `день`, помогает выбрать весь каталог. Алиас медиа, например `сонный кот`, описывает контекст одного файла. Ручные и автоматически сгенерированные алиасы медиа хранятся вместе в `media_search_aliases` и участвуют в поиске одинаково, без отдельной индексации. Техническое имя файла в контекстном поиске не участвует.

| Ввод после `@имя_бота` | Режим | Результат |
| --- | --- | --- |
| пусто | выбор категории | по одному случайному медиа из каждой активной категории |
| `day` или `день` | поиск категории | весь каталог всех категорий, частично совпавших по имени или алиасу |
| `кот` | глобальный поиск медиа | медиа из всех активных категорий, у которых алиас содержит `кот` |
| `кот спит` | глобальный AND-поиск | каждое слово должно частично совпасть хотя с одним алиасом того же медиа |
| `day кот` или `день кот` | поиск медиа в категории | первое слово выбирает категорию, оставшиеся ищут медиа только внутри неё |

Одно слово сначала проверяется как частичное имя или алиас категории; глобальный поиск медиа начинается, только если категория не найдена. В запросе из нескольких слов первое слово считается категорией только при точном совпадении с её именем или с ровно одним уникальным однословным алиасом. Точное имя имеет приоритет, а неоднозначный алиас оставляет весь запрос глобальным.

Регистр, внешние пробелы и разница между видами whitespace не учитываются; совпадение токена с алиасом частичное. Медиа без алиасов не находится контекстным поиском, но по-прежнему попадает в полную выдачу категории. Неизвестный контекст возвращает пустую выдачу.

Продолжение inline-выдачи загружается штатной пагинацией Telegram. Первая страница содержит специальный случайный результат и до 49 обычных, а следующие страницы — до 50 обычных результатов. Бот передаёт между страницами самодостаточный версионированный cursor с seed последовательности и числовой позицией; cursor привязан к нормализованному тексту запроса, укладывается в ограничение Telegram 64 байта и не хранится в Redis. Отдельного TTL у cursor нет: он остаётся формально действительным для того же запроса, пока бот поддерживает его версию.

Отсутствие повторов и пропусков гарантируется, пока между страницами не меняются дедуплицированный каталог подходящих медиа и состояние их готовности в Telegram. В частности, первая materialization MP4 добавляет его в доступный inline-каталог. Такие изменения обрабатываются best effort без серверного snapshot. Невалидный, слишком длинный, неизвестной версии или относящийся к другому запросу cursor не перезапускает последовательность с произвольной позиции: бот возвращает пустую последнюю страницу. Временные URL запрашиваются только для `pending`-фото и GIF текущей страницы, а не для уже пройденных или ещё не показанных результатов; `ready`-медиа всех типов использует Telegram `file_id`.

## Технологии

- **Python 3.14** и [aiogram 3](https://docs.aiogram.dev/) — асинхронный Telegram-бот в режиме long polling;
- **aiohttp** — работа с REST API Яндекс Диска и native API Ollama;
- **Pillow** и **PyAV** — подготовка статичного кадра для автоматических алиасов; отдельный исполняемый файл `ffmpeg` не требуется в штатном production-образе;
- **PostgreSQL 18**, **SQLAlchemy 2.1** и **asyncpg** — категории, папки подписок, медиа-каталог, Telegram `file_id`, пользовательские циклы, подписки и очередь обогащения алиасов;
- **Redis** с **hiredis** — защита рассылок от дублирования и распределённые lease;
- **uv** — управление зависимостями и запуск приложения;
- **Docker Compose** — запуск бота, PostgreSQL и Redis;
- **pytest**, **Ruff** и **mypy** — функциональные тесты, линтинг и проверка типов в CI.

## Развёртывание на своём сервере

### Что понадобится

- Linux-сервер с Git, Docker Engine и Docker Compose v2;
- PostgreSQL 18: миграция медиа-каталога использует виртуальную generated-колонку, которой нет в более старых версиях;
- Telegram-бот и его токен от [@BotFather](https://t.me/BotFather);
- OAuth-токен Яндекс Диска с доступом к папке приложения;
- исходящие HTTPS-подключения к Telegram Bot API и API Яндекс Диска.

Входящий HTTP-порт для бота открывать не нужно: обновления Telegram он получает через long polling. Файл `compose.yml` публикует PostgreSQL на порту `4243`, а Redis — на `12312`; ограничьте доступ к ним сетевым экраном сервера, если эти порты не нужны извне.

### 1. Получить проект

```bash
git clone https://github.com/progbagger/cringe-pics-telebot.git
cd cringe-pics-telebot
```

### 2. Настроить переменные окружения

Создайте четыре обязательных файла. Они игнорируются Git и не должны попадать в репозиторий.

`docker/bot/.env`:

```dotenv
TELEGRAM_BOT_TOKEN=<токен Telegram-бота>
```

`docker/postgres/.env`:

```dotenv
POSTGRES_USER=cringe_bot
POSTGRES_PASSWORD=<надёжный пароль PostgreSQL>
POSTGRES_DB=cringe_bot
POSTGRES_HOST=postgres
```

`docker/redis/.env`:

```dotenv
REDIS_USERNAME=cringe_bot
REDIS_PASSWORD=<надёжный пароль Redis>
REDIS_HOST=redis
```

`docker/yandex/.env`:

```dotenv
YANDEX_DISK_TOKEN=<OAuth-токен Яндекс Диска>
```

Чтобы отправлять метрики на существующий внешний Graphite/StatsD, скопируйте пример и укажите доступный из bot container адрес StatsD:

```bash
cp docker/statsd/.env.example docker/statsd/.env
```

```dotenv
STATSD_HOST=statsd.example.com
STATSD_PORT=8125
STATSD_PREFIX=cringe_pics_telebot
```

StatsD использует UDP. Проект не запускает Graphite и не управляет его хранилищем или dashboard; на внешнем сервере и в firewall должен быть разрешён UDP-трафик от bot host к указанному порту. Если `docker/statsd/.env` отсутствует, метрики отключены. Если endpoint настроен, но port некорректен или адрес не разрешается, бот завершает startup с явной ошибкой конфигурации. Ошибка UDP-отправки после успешного запуска не останавливает polling.

Дополнительно в `docker/bot/.env` можно задать:

- `LOG_LEVEL_NAME`;
- `SUBSCRIPTION_BROADCAST_INTERVAL_SECONDS` и `ADMIN_BROADCAST_INTERVAL_SECONDS` — интервалы проверки периодических рассылок и административных уведомлений соответственно, по умолчанию 30 секунд; допустимы значения больше нуля и не более 60 секунд;
- `MEDIA_SYNC_INTERVAL_SECONDS` — интервал общего цикла синхронизации медиа с Яндекс Диска и дней рождения из профилей Telegram, по умолчанию `43200` секунд (12 часов). Первый проход обоих этапов выполняется сразу после запуска; значение должно быть больше нуля.

#### Опционально: автоматические алиасы через Ollama

По умолчанию фича выключена. Для включения добавьте в `docker/bot/.env`:

```dotenv
MEDIA_ALIAS_ENRICHMENT_ENABLED=true
OLLAMA_BASE_URL=https://ollama.example.com
OLLAMA_MODEL=<имя установленной на endpoint vision-модели>
MEDIA_ALIAS_LLM_PROMPT="Опиши контекст изображения короткими русскими и английскими поисковыми фразами. Верни JSON-объект с единственным ключом aliases: массив от 1 до 20 непустых строк, каждая не длиннее 100 символов."
# Только если endpoint требует bearer token:
# OLLAMA_API_KEY=<токен защищённого endpoint>
```

Чтобы не копировать prompt в `.env`, сохраните его в локальном файле и вместо `MEDIA_ALIAS_LLM_PROMPT` задайте:

```dotenv
MEDIA_ALIAS_LLM_PROMPT_FILE=/app/ollama-media-alias-prompt.md
```

Удалите `MEDIA_ALIAS_LLM_PROMPT` из окружения либо оставьте пустым: при включённой фиче нужен ровно один непустой источник. Два источника одновременно или отсутствие обоих — ошибка startup. При выключенной фиче оба игнорируются, файл не проверяется и не читается. Не используйте `$(cat …)` в `.env`: shell-команда не выполняется. Файл читает сам бот, только если задан `MEDIA_ALIAS_LLM_PROMPT_FILE`.

Файл должен быть обычным, доступным для чтения, в UTF-8 (BOM допустим), размером не больше 64 KiB (`65536` байт), и содержать только текст prompt. Расширение `.md` допустимо, но Markdown не разбирается: заголовки и fenced-блоки не извлекаются, текст передаётся целиком после удаления BOM и внешних пробелов. Не добавляйте внешние инструкции подключения или ограждение кодового блока. Пустой/whitespace-only, отсутствующий, недоступный или не-UTF-8 файл, каталог/FIFO и превышение лимита останавливают startup до подключения внешних клиентов; содержимое prompt не выводится в диагностике.

Путь задаётся внутри процесса бота. В текущем Compose каталог проекта смонтирован read-only в `/app`: для примера выше файл должен находиться в корне проекта на сервере. Сам локальный prompt не включайте в Git; доставьте его на сервер отдельно. Относительный путь разрешается от working directory (в Compose — `/app`), а не от каталога `.env`. Сам загрузчик бота не раскрывает `~`, переменные окружения внутри пути и shell-подстановки.

Бот использует [native `POST /api/chat`](https://docs.ollama.com/api/chat), а не OpenAI-compatible API: передаёт prompt и один JPEG в `messages[].images` как base64 без data URL, задаёт `stream=false`, `temperature=0` и JSON Schema через `format`. Endpoint и выбранная модель должны поддерживать изображения и structured outputs. По текущей [документации Ollama](https://docs.ollama.com/capabilities/structured-outputs) Ollama Cloud structured outputs не поддерживает; одного API key для совместимости недостаточно. Развёртывание Ollama, установка модели и настройка GPU выполняются отдельно: Compose проекта запускает только бота, PostgreSQL и Redis.

Локальный API Ollama [не требует аутентификации](https://docs.ollama.com/api/authentication): не публикуйте его напрямую в Интернет. Используйте закрытую сеть/VPN либо защищённый reverse proxy с TLS termination и проверкой bearer token. Endpoint должен быть доступен из контейнера бота; `localhost` внутри него означает сам контейнер. Через HTTP обращайтесь только в доверенной изолированной сети. `OLLAMA_API_KEY` лишь добавляет заголовок `Authorization: Bearer …`; защиту на стороне сервера нужно настроить отдельно. Prompt, токен и `.env` не должны попадать в Git или вывод диагностических команд.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MEDIA_ALIAS_ENRICHMENT_ENABLED` | `false` | Включить enqueue и фоновый worker |
| `OLLAMA_BASE_URL` | нет | Обязательный корневой HTTP(S) URL, без `/api`, другого пути, credentials, query и fragment; завершающий `/` допустим |
| `OLLAMA_MODEL` | нет | Обязательное имя vision-модели на endpoint |
| `MEDIA_ALIAS_LLM_PROMPT` | нет | Непустой prompt для генерации алиасов; задайте его либо `MEDIA_ALIAS_LLM_PROMPT_FILE` |
| `MEDIA_ALIAS_LLM_PROMPT_FILE` | нет | Альтернативный источник: путь к UTF-8 файлу с текстом prompt, не больше 64 KiB |
| `OLLAMA_API_KEY` | нет | Необязательный bearer token; пустое значение не добавляет `Authorization` |
| `OLLAMA_REQUEST_TIMEOUT_SECONDS` | `120` | Полный timeout HTTP-запроса к модели |
| `MEDIA_ALIAS_ENRICHMENT_CONCURRENCY` | `2` | Максимум одновременно обрабатываемых заданий в одном процессе |
| `MEDIA_ALIAS_ENRICHMENT_POLL_INTERVAL_SECONDS` | `5` | Пауза между проходами при неполном batch |
| `MEDIA_ALIAS_ENRICHMENT_LEASE_TTL_SECONDS` | `300` | Срок владения заданием без heartbeat |
| `MEDIA_ALIAS_ENRICHMENT_LEASE_REFRESH_SECONDS` | `60` | Интервал продления lease |
| `MEDIA_ALIAS_ENRICHMENT_MAX_ATTEMPTS` | `5` | Бюджет попыток в одном retry-cycle, включая первую |
| `MEDIA_ALIAS_ENRICHMENT_RETRY_BASE_SECONDS` | `30` | Начальная задержка повторной попытки |
| `MEDIA_ALIAS_ENRICHMENT_RETRY_MAX_SECONDS` | `3600` | Верхняя граница экспоненциальной задержки |
| `MEDIA_ALIAS_ENRICHMENT_DOWNLOAD_TIMEOUT_SECONDS` | `60` | Полный timeout скачивания исходного файла |
| `MEDIA_ALIAS_ENRICHMENT_MAX_SOURCE_BYTES` | `20971520` | Максимум скачиваемых исходных данных: 20 MiB |
| `MEDIA_ALIAS_ENRICHMENT_MAX_FRAME_PIXELS` | `40000000` | Максимум пикселей исходного кадра до уменьшения |
| `MEDIA_ALIAS_ENRICHMENT_MAX_IMAGE_EDGE_PIXELS` | `1280` | Максимальная сторона подготовленного JPEG |
| `MEDIA_ALIAS_ENRICHMENT_MAX_IMAGE_BYTES` | `4194304` | Максимальный размер JPEG до base64: 4 MiB |

Все числовые значения должны быть положительными; количества и лимиты — целыми, интервалы и timeout допускают дробные конечные секунды. Интервал heartbeat должен быть меньше TTL, а максимальная retry-задержка — не меньше начальной. При включённой фиче ошибки конфигурации останавливают startup до создания внешних клиентов. При выключенной остальные Ollama/worker-настройки игнорируются: клиент, HTTP-сессия, worker и новые задания не создаются, уже сохранённые задания остаются в PostgreSQL.

Настройки, включая текст prompt, загружаются один раз при старте: worker, ручная и фоновая синхронизации используют один startup snapshot. Hot reload нет. SHA-256 задания рассчитывается от фактически используемого текста, после удаления BOM и внешних пробелов у файлового варианта. После изменения `.env` или prompt-файла пересоздайте контейнер бота командой `docker compose up -d --force-recreate bot`. Изменение prompt не перегенерирует уже заполненные алиасы. Первый успешный sync поставит подходящие старые и новые медиа в очередь; ждать завершения модели перед использованием бота не нужно.

### 3. Подготовить медиа на Яндекс Диске

Создайте в папке приложения на Яндекс Диске каталоги категорий и загрузите туда изображения, GIF или MPEG-4 с MIME-типом `video/mp4`. MP4 должен быть не больше 20 MiB (`20 * 1024 * 1024` байт): при текущей архитектуре Telegram сам загружает файл по временному HTTP URL. Другие видеоконтейнеры и более крупные MP4 пропускаются с диагностичным warning-логом; бот не отправляет их как `document` и не скачивает для multipart-загрузки. Для стандартного набора каталогов это:

```text
morning/
day/
evening/
night/
random/
```

Имена каталогов должны совпадать со значениями `s3_directory_path` в таблице `subscription_types` из шага добавления категорий.

### 4. Запустить сервисы

Production Compose закреплён на PostgreSQL 18. Если существующий volume создан PostgreSQL 17 или более ранней версией, сначала сделайте резервную копию и перенесите кластер в PostgreSQL 18 через `pg_upgrade` или dump/restore. Нельзя подключать `postgres:18` непосредственно к data directory старой major-версии. На чистой установке дополнительных действий не требуется.

```bash
docker compose run --rm bot uv run --isolated --no-dev --group migration alembic upgrade head
docker compose up -d --build
docker compose ps
docker compose logs -f bot
```

Миграции Alembic запускаются отдельной одноразовой командой и не входят в production-зависимости процесса бота. После запуска polling можно остановить просмотр логов сочетанием `Ctrl+C` — контейнеры продолжат работать.

### 5. Добавить администраторов

Список администраторов хранится в таблице `administrators`. Получите Telegram user ID нужного пользователя и добавьте его следующей командой, заменив `123456789` реальным значением:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
INSERT INTO administrators (user_id)
VALUES (123456789)
ON CONFLICT (user_id) DO NOTHING;
SQL
```

Права применяются без перезапуска бота. Чтобы отозвать их, удалите только запись из `administrators`:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
DELETE FROM administrators WHERE user_id = 123456789;
SQL
```

После добавления ID кнопка **Админ-панель** появится с подходящим новым сообщением после обновления кеша интерфейса (TTL 60 секунд), без обязательного `/start`. Команда `/admin` доступна сразу; удаление ID сразу отзывает доступ, даже если кнопка ещё видна до обновления кеша. Для остальных пользователей команда и текст кнопки обрабатываются как неизвестное сообщение.

### 6. Добавить категории

Пример ниже создаёт стандартные категории и задаёт локальное время рассылок. Повторный запуск команды обновит существующие записи.

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
INSERT INTO subscription_types (
    name,
    time,
    weekdays,
    schedule_kind,
    annual_month,
    annual_day,
    s3_directory_path,
    search_aliases,
    is_active,
    created_at,
    updated_at
)
VALUES
    ('random',  '00:00:00', 127, 'weekly', NULL, NULL, 'random',  ARRAY['рандом', 'случайная'],        true, now(), now()),
    ('morning', '08:00:00', 127, 'weekly', NULL, NULL, 'morning', ARRAY['утро', 'утренняя', 'с утра'], true, now(), now()),
    ('day',     '13:00:00', 127, 'weekly', NULL, NULL, 'day',     ARRAY['день', 'дневная'],            true, now(), now()),
    ('evening', '19:00:00', 127, 'weekly', NULL, NULL, 'evening', ARRAY['вечер', 'вечерняя'],          true, now(), now()),
    ('night',   '23:00:00', 127, 'weekly', NULL, NULL, 'night',   ARRAY['ночь', 'ночная'],             true, now(), now())
ON CONFLICT (name) DO UPDATE
SET time = EXCLUDED.time,
    weekdays = EXCLUDED.weekdays,
    schedule_kind = EXCLUDED.schedule_kind,
    annual_month = EXCLUDED.annual_month,
    annual_day = EXCLUDED.annual_day,
    s3_directory_path = EXCLUDED.s3_directory_path,
    search_aliases = EXCLUDED.search_aliases,
    updated_at = now();
SQL
```

Название активной категории используется в подписи кнопки и в inline-поиске независимо от наличия расписания; добавлять к нему `/` не нужно. `search_aliases` задаёт дополнительные термины только для inline-поиска: запрос сопоставляется с именем и каждым алиасом без учёта регистра, по частичному совпадению. Алиасы не создают отдельные кнопки или подписки и не влияют на обычные сообщения.

Время указывается без UTC-смещения. `schedule_kind` принимает три значения:

- `weekly` использует `weekdays` — битовую маску ISO-дней: младший бит означает понедельник, следующий — вторник, …, седьмой — воскресенье. Значение `127` включает все семь дней, а `21` соответствует `Пн, Ср, Пт`;
- `annual_date` требует `annual_month` и `annual_day`, например `1, 1` для Нового года;
- `annual_birthday` сравнивает локальную дату с `users.birth_month` и `users.birth_day` конкретного подписчика; пользователь без сохранённой даты пропускается независимо от остальных получателей.

Для `weekly` и `annual_birthday` поля `annual_month`/`annual_day` должны быть `NULL`. Для `annual_date` они должны образовывать настоящую календарную дату. `29.02` допустимо, но scheduler отправляет такую категорию только 29 февраля високосного года и не переносит её на соседнюю дату. Маска `weekdays` остаётся обязательной в каждом режиме; PostgreSQL допускает только значения `1..127`. Постоянные server defaults — `weekly` и `127`, поэтому старые и прямые `INSERT` без новых полей сохраняют ежедневное поведение.

Scheduler вычисляет локальные дату и время отдельно для каждого подписчика, поэтому одна annual-категория может отправиться разным пользователям в разные UTC-минуты и даже UTC-даты. Например, фиксированную ежегодную категорию можно добавить так:

```sql
INSERT INTO subscription_types (
    name, time, weekdays, schedule_kind, annual_month, annual_day,
    s3_directory_path, search_aliases, is_active, created_at, updated_at
)
VALUES (
    'new-year', '12:00:00', 127, 'annual_date', 1, 1,
    'new-year', ARRAY['новый год'], false, now(), now()
);
```

Значение `NULL` вместо времени временно отключает расписание: после активации категория появится в reply-клавиатуре и inline-режиме, но не в списке подписок или scheduler. Существующие подписки, `schedule_kind`, маска дней и fixed date при этом не очищаются и снова применяются после задания времени. Путь задаётся относительно папки приложения на Яндекс Диске. Категория `random` в этом примере является отдельной коллекцией и отдельной рассылкой; при необходимости её можно удалить или настроить как любую другую категорию.

На уровне PostgreSQL новые категории имеют `is_active = false` по умолчанию. Пример выше явно активирует первоначальный стандартный набор. Повторный запуск команды обновляет поля категории, но намеренно не меняет `is_active`, поэтому не включит категорию, которую администратор ранее деактивировал.

После первоначального добавления категорий откройте `/admin` и нажмите **Синхронизировать медиа**, чтобы без перезапуска немедленно синхронизировать медиа-каталог и доступные дни рождения из профилей Telegram. После завершения отправьте боту `/start`.

При необходимости смените часовой пояс командой, например `/timezone +04:00`. Последующие добавления, изменения и удаления файлов попадут в каталог при очередном автоматическом цикле или после ручного запуска из админ-панели; период фоновой синхронизации данных задаётся `MEDIA_SYNC_INTERVAL_SECONDS`. Ошибка чтения одной папки не деактивирует её предыдущий успешный snapshot. Для проверки состояния и логов используйте:

```bash
docker compose ps
docker compose logs --tail=100 bot
```

### 7. Настроить папки подписок

Папки можно создавать и заполнять через **Админ-панель → Управление папками**. Для первоначальной настройки через SQL следующий пример создаёт папку **Праздники** и добавляет существующие категории `new-year`, `birthday` и `halloween`:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
WITH folder AS (
    INSERT INTO subscription_category_folders (name)
    VALUES ('Праздники')
    ON CONFLICT (name) DO UPDATE SET updated_at = now()
    RETURNING id
)
INSERT INTO subscription_category_folder_members (folder_id, subscription_type_id)
SELECT folder.id, category.id
FROM folder
JOIN subscription_types AS category
    ON category.name IN ('new-year', 'birthday', 'halloween')
ON CONFLICT (subscription_type_id) DO NOTHING;
SQL
```

Повторный запуск не создаёт дубли. Категория, уже входящая в другую папку, остаётся там: сначала удалите её прежнюю запись membership либо используйте админ-панель. Одна категория может входить максимум в одну папку, а папка содержит только строки `subscription_types`, поэтому вложенные папки не поддерживаются.

В пользовательском меню видны папки с хотя бы одной активной категорией и включённым расписанием. Пустые папки, неактивные категории и категории с `time IS NULL` остаются сохранёнными и доступны администратору, но скрываются из `/list` и `/subscriptions` до появления подходящего элемента. Массовые кнопки внутри папки изменяют подписки только на её текущие активные категории с расписанием.

Обновление установленной версии выполняется так:

```bash
git pull --ff-only
docker compose run --rm bot uv run --isolated --no-dev --group migration alembic upgrade head
docker compose up -d --build --remove-orphans
```

При запуске без Docker Compose сначала примените миграции командой `uv run --isolated --no-dev --group migration alembic upgrade head`, а затем запустите бота командой `uv run --no-dev bot`.

Данные PostgreSQL, включая медиа-каталог, Telegram `file_id`, пользовательские циклы отправки и очередь обогащения алиасов, а также виртуальное окружение бота сохраняются в Docker volumes `pg-data` и `bot-env`. Redis содержит только восстанавливаемые dedupe/lease-ключи и отдельного volume не имеет.

## Управление категориями через админ-панель

Администратор может открыть **Админ-панель → Управление категориями**, увидеть статусы всех категорий и создать новую. После названия и пути бот предлагает четыре режима:

- **По дням недели**: локальное время в формате `ЧЧ:ММ` → дни → поисковые алиасы. Дни переключаются кнопками `Пн`…`Вс`; **Готово** принимает непустой выбор, а **Каждый день** выбирает все семь дней;
- **Раз в год — фиксированная дата**: дата в строгом формате `ДД.ММ` → алиасы. Новая категория получает локальное время `12:00`;
- **Раз в год — день рождения подписчика**: сразу алиасы; локальное время новой категории также равно `12:00`;
- **Без расписания**: сохраняется `weekly + time=NULL` с ежедневной маской, а шаги времени и дней пропускаются.

Время annual-категории можно изменить после создания. До заполнения последнего шага данные находятся только в черновике FSM; неверная дата или отмена не создаёт частичную запись. Новая категория всегда создаётся неактивной.

Список категорий сортируется по названию и показывает до восьми категорий на странице. Кнопки `←` и `→` редактируют текущее сообщение; после просмотра карточки, изменения категории или отмены формы бот возвращает администратора на ту же страницу. Если удаление или изменение состава списка делает её недоступной, бот открывает последнюю существующую страницу.

Карточка категории показывает русское описание: например, `каждый день в 13:00`, `ежегодно 01.01 в 12:00` или `ежегодно в день рождения подписчика в 12:00`. **Изменить вид расписания** доступно и при отключённом времени. Для `weekly` показывается **Изменить дни отправки**, для `annual_date` — **Изменить ежегодную дату**, а birthday-режим не запрашивает общую дату категории. Смена режима атомарно записывает согласованный вид и fixed date, не меняя время, название, путь, алиасы, активность, медиа или подписки. Неверная дата и отмена оставляют прежнее состояние.

**Изменить время отправки** задаёт новое `ЧЧ:ММ` или повторно включает расписание. **Отключить расписание** скрывает категорию из списка подписок и останавливает плановые отправки, сохраняя вид и параметры расписания, ordinary- и inline-выдачу. Существующие подписки не удаляются: после повторного задания времени они снова становятся видимыми и действующими с прежним видом, днями или fixed date.

Birthday-режим использует сохранённые `users.birth_month`, `users.birth_day` и `birthdate_source`. Пользователь может задать их командой `/birthday`, а при отсутствии ручного значения бот поддерживает дату по данным Telegram-профиля. Подсказка в `/list` и `/subscriptions` появляется только пока дата не сохранена.

Кнопки **Активировать** и **Деактивировать** управляют доступностью категории без перезапуска бота. Неактивная категория исчезает из пользовательских кнопок, списка подписок и inline-поиска, а плановые отправки для неё приостанавливаются. Медиа-каталог и существующие подписки при этом не удаляются: каталог продолжает синхронизироваться, а после повторной активации сохранённые подписки снова действуют.

Алиасы категории вводятся по одному на строку; внешние пробелы удаляются, а пустые строки и повторы без учёта регистра игнорируются. Кнопка **Очистить алиасы** удаляет весь дополнительный словарь, не меняя основное имя, статус, подписки, расписание или путь к медиа. Первичную инициализацию и идемпотентное массовое обновление категорий по-прежнему удобнее выполнять SQL-командой из раздела выше.

Кнопка **Медиа и алиасы** открывает список активных медиа категории по восемь элементов на странице. Карточка медиа показывает имя, путь, тип, статус каталога и текущие контекстные алиасы. **Изменить алиасы медиа** открывает форму полной замены списка и отправляет рядом предпросмотр фото, GIF или видео. Для прогретого медиа предпросмотр использует Telegram `file_id`, для `pending` — свежую временную ссылку Яндекс Диска. Новые алиасы вводятся по одному на строку; пустой список отклоняется, а для удаления всех алиасов есть отдельная кнопка **Очистить алиасы медиа**. Возврат из карточки и формы сохраняет страницы списков медиа и категорий.

## Управление папками подписок через админ-панель

Раздел **Админ-панель → Управление папками** показывает все папки, включая пустые, по восемь на странице. Администратор может создать папку, переименовать её, открыть состав или удалить с отдельным подтверждением. Название после удаления внешних пробелов должно оставаться непустым и быть уникальным.

Редактор папки показывает все низкоуровневые категории независимо от активности и наличия расписания:

- `✅` — категория входит в открытую папку; нажатие удаляет membership;
- `❌` — категория свободна; нажатие добавляет её в открытую папку;
- `📁` и название другой папки — категория уже сгруппирована. Для переноса сначала откройте прежнюю папку и удалите категорию из неё.

Создание, переименование и изменение состава выполняются короткими транзакциями PostgreSQL. Callback повторно проверяет папку, категорию и актуальный membership, поэтому устаревшая кнопка не переносит и не удаляет другой объект. Список и редактор сохраняют открытую страницу после действия.

Удаление папки каскадно удаляет только строки `subscription_category_folder_members`. Категории, их медиа, расписания и пользовательские подписки сохраняются; подходящие категории сразу возвращаются в корень пользовательского списка. Удаление категории, пока она состоит в папке, запрещает внешний ключ `ON DELETE RESTRICT`. Удаление самой папки использует `ON DELETE CASCADE` для membership.

В `/list` и `/subscriptions` папки отображаются перед несгруппированными категориями. Внутри доступны отдельные переключатели, **Подписаться на все**, **Отписаться от всех** и **Назад**. Массовые операции атомарны и идемпотентны. Названия папок не участвуют в ручной выдаче, reply-клавиатуре и inline-поиске; там остаются входящие в них низкоуровневые категории.

### Ручная синхронизация медиа и профилей

Кнопка **Синхронизировать медиа** с сохранённой для совместимости подписью находится на верхнем уровне админ-панели. Бот сразу подтверждает запуск и последовательно выполняет два этапа. Сначала он обходит все категории, включая неактивные, и формирует сводку по медиа: количество обработанных категорий и ошибок, найденных медиа, созданных и изменённых записей, повторно активированных медиа, деактивированных отсутствующих файлов и поставленных заданий на алиасы. Последний счётчик означает enqueue, а не завершённую генерацию; при выключенной фиче он равен нулю. Синхронизация не ждёт модель. Ошибка отдельной категории отображается как частично успешный результат и не скрывает счётчики успешно обработанных категорий.

Затем бот синхронизирует профили всех известных пользователей, включая неактивных для рассылок, страницами по 100 записей и не более чем пятью одновременными запросами `getChat`. Ручные значения пропускаются без запроса к Telegram. Доступная дата создаёт или обновляет Telegram-значение; если успешный ответ больше не содержит birthdate, бот очищает только ранее полученное из Telegram значение. Год из профиля игнорируется. При Telegram `429` запрос повторяется ровно один раз после указанной задержки, а остальные ошибки сохраняют прежнее состояние пользователя и не останавливают обработку других профилей.

Администратор получает отдельные сводки по медиа и профилям, включая число созданных, обновлённых и очищенных дат, пропущенных ручных значений, профилей без даты и ошибок. Этапы изолированы: ошибка или занятый lease одного этапа не отменяет и не скрывает результат другого. Ручной и фоновый запуски используют общий orchestration, но отдельный Redis lease для каждого этапа, поэтому параллельно не выполняются только одноимённые обходы. Логи содержат идентификаторы, классы ошибок и итоговые счётчики без дат рождения, имён и полных ответов Telegram. После любого результата можно запустить синхронизацию повторно или вернуться в админ-панель.

## Автоматическое обогащение алиасов

При включённой фиче каждый успешный sync категории атомарно сохраняет каталог и ставит задания для всех активных медиа без алиасов: старых и новых, `pending` и `ready`, в том числе из неактивных категорий. Неактивные файлы и медиа с любыми существующими алиасами пропускаются. Если папку не удалось прочитать, её прежний snapshot сохраняется, но задания для неё в этом проходе не ставятся.

Очередь `media_alias_enrichment_jobs` создаётся миграцией `0014`; пара `media_id + source_revision` уникальна. Статусы: `pending` — ожидает, `processing` — занят worker-ом, `retry` — ждёт `available_at`, `succeeded` — алиасы сохранены, `failed` — ошибка или исчерпан бюджет, `obsolete` — медиа больше не подходит. PostgreSQL row locks и lease token разделяют задания между процессами; concurrency ограничивается отдельно в каждом процессе. Сетевые запросы и декодирование выполняются вне транзакций PostgreSQL и вне Redis lease синхронизации.

На каждой попытке worker получает свежую временную ссылку Яндекс Диска и скачивает файл с timeout и ограничением байт, не пересылая OAuth-токен скачивающему endpoint. Фото учитывает EXIF-ориентацию; GIF использует средний кадр по индексу; MP4 — кадр около середины длительности, при невозможности выбора — первый декодируемый. CPU-декодирование вынесено из event loop. Кадр проверяется по числу пикселей, преобразуется в RGB JPEG, уменьшается по стороне и размеру и только затем отправляется модели. Целый GIF/MP4 не передаётся в Ollama. Лимиты обогащения независимы от допуска MP4 в каталог и не меняют формат отправки в Telegram.

Ответ должен содержать JSON в `message.content`: объект только с полем `aliases`, массив из 1–20 строк по 1–100 Unicode-символов. Бот удаляет внешние пробелы, сворачивает whitespace и убирает дубли без учёта регистра, сохраняя первый вариант. Пустые или некорректные алиасы отклоняются. Перед записью повторно проверяются lease, активность медиа, текущая revision и отсутствие алиасов. Ручная запись во время LLM-запроса выигрывает и не перезаписывается; устаревший результат не применяется, а для актуальной revision при необходимости ставится новое задание. Генерация не меняет Telegram `file_id` и статус `pending`/`ready`.

Сетевые ошибки, timeout, HTTP `429`/`5xx` и некорректный ответ повторяются с экспоненциальным backoff до бюджета попыток. Другие HTTP-ошибки, неподдерживаемый тип, ошибка декодирования и превышение лимитов сразу завершают задание как `failed`. Ошибка одного задания не мешает остальным, polling, inline-выдаче и обычным/плановым отправкам. Heartbeat продлевает только действующий lease; после аварии истёкшее `processing` может забрать другой worker. Штатная остановка отменяет работу и освобождает принадлежащие процессу задания для повторной попытки; начатое декодирование дожидается освобождения ресурсов.

Следующий успешный sync может повторно открыть терминальное задание, если медиа всё ещё активно и без алиасов: retry-бюджет сбрасывается, но общий `attempt_count` сохраняется. **Очистить алиасы медиа** позволяет повторное обогащение при следующем sync, а не сразу после нажатия. Смена model/prompt не регенерирует уже заполненные алиасы; при следующем claim используются актуальные настройки, в задании фиксируются имя модели и SHA-256 prompt. Ручной список всегда можно заменить через карточку медиа.

### Наблюдение за очередью

В логах worker-а остаются идентификаторы задания/медиа, revision, модель, попытка, длительность и класс результата. Prompt, токен, исходные байты/base64, тексты алиасов, полный ответ модели и содержимое внешних ошибок не логируются; `last_error` хранит только имя типа ошибки.

При настроенном StatsD доступны метрики с префиксом `STATSD_PREFIX`: counters `media_alias_enrichment.{queued,claimed,succeeded,retry,failed,stale_revision,manual_aliases_won,inactive,unsupported,decode_failed,lease_lost}`, timings `media_alias_enrichment.{media_prepare,ollama_request}` и gauges `media_alias_enrichment.queue.{available,expired_processing,failed}`. `available` считает готовые к claim `pending`/`retry`, истёкшие `processing` показаны отдельно. Timings включают неуспешные и отменённые попытки соответствующего этапа. Ошибка отправки метрики не меняет результат задания.

Без StatsD можно проверить статусы read-only запросом:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT status, count(*) FROM media_alias_enrichment_jobs GROUP BY status ORDER BY status;
SELECT id, media_id, source_revision, status, attempt_count, retry_count,
       available_at, leased_until, model, result_class, last_error
FROM media_alias_enrichment_jobs
WHERE status IN ('retry', 'failed', 'processing')
ORDER BY updated_at DESC
LIMIT 20;
SQL
```

Для `failed` сначала устраните причину по классу результата и настройкам endpoint/лимитов, затем выполните **Синхронизировать медиа**. Отдельного UI мониторинга/retry и принудительной массовой регенерации нет.

## Разовые административные уведомления

Откройте `/admin`, выберите **Уведомления** и отправьте боту сообщение, которое нужно скопировать получателям. Поддерживаются типы сообщений, доступные методу Telegram `copyMessage`; исходное сообщение нельзя удалять до завершения отправки уведомления.

Список запланированных уведомлений показывает до четырёх записей на странице: каждое уведомление занимает две строки кнопок. Навигация `←` и `→`, просмотр, редактирование, удаление и отмена формы сохраняют открытую страницу; после удаления последней записи на странице бот переходит на последнюю существующую.

Дата вводится одним из двух способов:

```text
20.08.2099 10:00
20.08.2099 10:00 +07:00
```

В первом варианте каждый получатель получает сообщение, когда `10:00` наступает в его сохранённом часовом поясе. Во втором все получают сообщение одновременно — в момент, соответствующий `10:00 UTC+07:00`. Допустимые фиксированные смещения: от `-12:00` до `+14:00`.

После даты бот предлагает указать до 1000 дополнительных Telegram user ID через пробелы, запятые или переносы строк. Этот список нужен, например, для разовой отправки пользователям, которых старая версия бота ещё не сохраняла. Дополнительные ID относятся только к выбранному уведомлению и не делают пользователя постоянным получателем следующих. Если для ID ещё нет сохранённого часового пояса, используется значение по умолчанию `UTC+07:00`; явное смещение в дате по-прежнему задаёт один момент для всех. Шаг можно пропустить inline-кнопкой, а список — позднее изменить до начала отправки.

До начала первой доставки уведомление можно редактировать или удалить inline-кнопками. После начала отправки редактирование блокируется, чтобы пользователи разных часовых поясов не получили разные версии. Удаление является мягким: запись получает статус `deleted`, а завершённое уведомление — `completed`. Сами уведомления и результаты попыток остаются в PostgreSQL, хотя экран истории в текущей версии отсутствует.

Перед каждым сетевым запросом бот атомарно резервирует одну попытку для пары «уведомление — пользователь», поэтому повторная проверка scheduler-а не создаёт дубль. Автоматических повторов после ошибки нет; сбой одному получателю сохраняется в истории и не останавливает отправку остальным.

## Автоматический деплой через GitHub Actions

Workflow **Deploy over SSH** автоматически обновляет сервер после merge pull request в `main`, если workflow **CI** успешно проверил итоговый commit и были изменены файлы приложения или production-сборки:

- `src/**`;
- `docker/**`;
- `alembic/**` или `alembic.ini`;
- `pyproject.toml` или `uv.lock`;
- `compose.yml`.

Изменения только в документации, тестах и служебных файлах деплой не запускают. Workflow также можно запустить вручную через `workflow_dispatch`; ручной запуск не зависит от списка изменённых файлов.

В GitHub environment с именем **Deploy** нужно создать secrets:

- `DEPLOY_HOST` — адрес сервера;
- `DEPLOY_USER` — SSH-пользователь;
- `DEPLOY_SSH_KEY` — приватный SSH-ключ;
- `DEPLOY_PORT` — SSH-порт, если используется не `22`;
- `DEPLOY_PATH` — путь к checkout репозитория на сервере, если он отличается от `cringe-pics-telebot`.

Перед первым автоматическим деплоем репозиторий, `.env`-файлы, категории PostgreSQL и папки Яндекс Диска нужно подготовить вручную по инструкции выше. Workflow разворачивает конкретный commit, применяет миграции отдельным one-shot контейнером и перезапускает сервисы через Docker Compose.

Настройки Ollama добавляются в `docker/bot/.env` на сервере вручную, не в GitHub secrets деплоя: workflow не создаёт `.env` и не разворачивает модель. До включения проверьте доступность защищённого vision endpoint из контейнера бота. Если настройки не добавлены, обновление оставляет обогащение выключенным.

## Проверки разработки

```bash
uv sync --locked --all-extras --dev
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest tests/units -q
uv run pytest tests/functional -q
```

Функциональные fixtures поднимают PostgreSQL 18 и Redis через `tests/functional/compose.functional-tests.yml` на свободных локальных портах; нужен работающий Docker. Telegram, Яндекс Диск, Ollama и StatsD заменяются fake-сервисами, реальная модель и внешние токены не нужны. Тесты обогащения запускают процесс бота и проверяют HTTP-запросы, сохранённые алиасы, retry, recovery и гонки через управляемые barrier endpoints и время, без произвольных `sleep`. Проверки основной клавиатуры также работают через процесс бота, HTTP fake Telegram и SQL; тестовый runner управляет часами TTL и планировщиков. В тестовой PostgreSQL включён `pg_stat_statements`, чтобы считать чтения снимка при параллельных отправках снаружи приложения. CI запускает unit- и functional-наборы через `uv`; production запускает `uv run --no-dev bot`, включая Pillow/PyAV из основных зависимостей.
